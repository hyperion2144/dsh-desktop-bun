### 2.6 抽屉宽度（用户报「抽屉空白区域宽度与 UI 宽度不一致」）

**现象（实测，非目测）**：全量 profile 上抽屉列 **320px**、宿主侧栏内容 **280px** → 抽屉内部右侧 **40px 空白带**，且该带内 `elementFromPoint` 命中的是空壳列 `pI_x6G_sidebarCol`（**点它既不关抽屉也无任何反应**）。

**A/B 对照（活页面注入，不改源码；`~/tmp/diag/ab-width.mjs`）**：

| 注入 | 列宽 | 内容 | 内部空白 |
|---|---|---|---|
| baseline（无注入） | 320px | 280px | **40px** |
| `[data-dsh-frame] [data-pane="sidebar"]{width:max-content!important}` | 280px | 280px | **0** |
| 同上 `fit-content` / `280px` | 280px | 280px | 0 |
| 只改插件自身 `inset`（去掉左右边沿钉定） | 280px | 280px | 0（但破坏抽屉贴左，不采用） |

**断言门（`~/tmp/diag/assert-width.mjs`，6 断言）**：未修 → `no-internal-blank`、`beyond-drawer-is-backdrop` 2 项 FAIL；注入 `width:max-content !important` → 仅剩 `beyond-drawer-is-backdrop` FAIL，**且该项在修复后语义反转**：修复前命中空壳列（死区），修复后命中 `null`（CSS 像素，因为列已缩到 280px，x=292 处无元素可命中），需改写断言为"点该处是否关抽屉"而不是"命中谁"。

**判定**：宽度**不是插件定的**——插件规则 `width:max-content`（无 `!important`）+ `max-width:92vw` 是**上限**且从未命中；宿主 root 的 inline `width:280px`（`computeColumns`: 收起 56px / 展开 clamp 264–420，默认偏好 280）才是内容宽；把列撑到 320px 的是**第三方响应层**。修法=给插件那条 `width/max-width` 补 `!important`（同特异度下 `!important` 胜非 `!important`），使抽屉**永远贴合内容**，从而在两种 profile 上都不留空白带。

## 3. 根因清单（每条必须有取证）

### RC1 · 插件规则与宿主 `!important` 平局后由**文档顺序**决定，宿主更晚注入 → 宿主赢

- 现象：插件 `[class*="hHd-Xa_toggle"]{display:none !important}` 在 CSSOM 里存在、media 条件匹配、元素 `matches()` 为 true，但计算样式仍 `display:flex`。
- 取证（`~/tmp/diag/matched.mjs`，CDP `CSS.getMatchedStylesForNode`）：同一元素上同时匹配
  - 宿主：`[data-dsh-frame][data-sidebar-collapsed] [data-pane="sidebar"] [data-dsh-responsive-part="sidebar-toggle"] { display:inline-flex !important }`（特异度 0,4,0，媒体 ≤768px）
  - 插件：`[class*="hHd-Xa_toggle"] { display:none !important }`（特异度 0,2,0）
- 裁决：**平局不看特异度，看注入顺序**；宿主样式表在插件 `<style>` 之前，但 `!important` 同源同权重时比较声明顺序——实测宿主后来居上（宿主框架样式与插件注入顺序在不同宿主版本可能变化，属脆弱依赖）。
- 影响：任何"插件 `!important` vs 宿主 `!important`"的对抗都不稳定，必须**显式提高特异度**（例如加 `:root` / `html` 前缀 / 组合到宿主结构上）。

### RC2 · 插件 toggle 与宿主 rail 开关**几何重叠**且层级更低

- 现象：面板收起时用户点左上角，命中宿主 `hHd-Xa_iconButton hHd-Xa_toggle`（44×44 @ `[10,14]`），不是插件 `[data-mobile-nav="toggle"]`（28×28 @ `[8,12]`，z=2）。
- 影响：点"我们的抽屉按钮"实际触发宿主开关；展开后同位置又被 `.hHd-Xa_brand`（252×24 的"新建会话"品牌按钮）覆盖 → 两种状态下都点不到。

### RC1b · 依赖第三方 shim 的宿主属性 = 只在装了该第三方时可用（**本轮最重要**）

- 插件大量布局规则/效果依赖 `data-dsh-frame`、`data-pane="sidebar|conversation|details"`、`data-dsh-responsive-part`。
- 取证：宿主 0.1.5 安装包（`/data/data/com.termux/files/usr/lib/node_modules/@deepseek-ai/dsh`）全树扫描 → `data-dsh-frame` 0 命中、`data-pane` 0 命中；这些属性由 `@linxin666/dsh-web-all` 的 `COLUMN_SHIMS` + `RESPONSIVE_CSS` 注入。
- 影响：**用户"仅加载两个插件"时，凡以这些属性为锚的规则全部静默失效**（不是报错，是"看起来没毛病但功能没了"）。
- 待办：把这类锚点改为**同时兼容两种来源**（宿主结构类名子串 + 第三方属性），或在缺失时降级到结构选择器。

### RC3 · 状态行（TPS）在 0.1.5 不再命中插件的启发式

- 插件在 `[data-phase] [class*="_root"]` 中寻找位于 `_composerStack` 内、含 `/(turns|steps|LLM|轮|步)/` 文本、无 button、无输入框的行。
- 实测 0.1.5 的 composer stack 子结构为 `lXshSW_root`（38px 提示条）、`uV2eYG_root > uV2eYG_card`（输入卡）、`bOPqQW_root`（26px 行）——状态行候选文本不含上述关键词 → 标记未注入（count=0）。

## 5. 本轮修复（已落源码 + 已验证）

**修复**：`src/client/styles/layout.css.ts` 抽屉列规则

```diff
-  [data-mobile-nav="frame"] > :first-child {   width: max-content;    max-width: 92vw;    …
+  :root [data-mobile-nav="frame"] > :first-child { width: max-content !important; max-width: 92vw !important; …
```

两处改动、都必要：

1. `!important`：对手 `[data-dsh-frame] [data-pane="sidebar"] { width: min(88vw,320px) !important }`（**来自 `@linxin666/dsh-web-all`**）带 `!important`，无 `!important` 的声明必然输。

### 11.1 撤回：标签行收起是错的（用户反馈「对话/轨迹栏消失了」）

§10.2 的"≤2 标签收起标签行"按用户先前选择实施，但用户随后明确反馈**轨迹栏消失**——那一行是切 Chat/Trajectory 的**唯一入口**，44px 是功能不是空白。**已整块撤回**（33 行全部删除，`wSkVaW_tabs` 在 layout.css.ts 归零），实测恢复：`tabsDisplay:flex`、header 97px、两个标签都可命中。
教训：**"省空间"类改动必须确认它隐藏的是不是用户的唯一入口**；`:nth-child` 计数门虽然让标签多时自动回来，但用户在 2 标签状态下就已经失去了入口。

### 11.2 文件按钮：宿主换控件导致的"点了没反应"（已修）

- 宿主在两种状态下**换按钮**（实测）：面板**关**时只有 `data-sidebar-right-expand`（0×0，但 click 有效）；面板**开**时 expand **被卸载**，只剩 `data-sidebar-right-toggle`（28×28，"收起右侧边栏"）。
- 我原本只点 expand → **面板已经开着时点我们的 Files 按钮 = 空操作**。而且面板是全屏的，会盖住 header，所以"第二次点不动"也由此而来。
- 修法：`openFilesPanel()` 改**开关语义**（有 opener 点 opener，否则点 closer），单测补两条（已开时用 closer / 两者都在时优先 opener）。真机门 `verify-files-toggle.mjs` 4/4：关→开→关→再开。

### 11.3 "右上三个点"：宿主把它自己的下拉菜单裁掉了（宿主 bug，已在我们这侧绕过）

- 该按钮是**官方 `@deepseek-ai/dsh-session-log-export`** 的 More actions（`nL4_yW_moreButton`，内含三段 2px SVG 组成 `···`），菜单项只有一项 `Download session log`。
- **真根因**：宿主把菜**单挂在 44×44 的 `wSkVaW_headerUtilities` 格子里，而该格子 `overflow: auto`** → 218×52 的菜单被裁进 44×44，**完全不绘制**。铁证：菜单计算样式 `flex / visible / opacity 1`，但 `elementsFromPoint(菜单项中心)` 的绘制栈里**没有菜单**，最上层是 `wSkVaW_tabs`；`elementsFromPoint` 全栈只有 tabs/header/centerCol/frame/body/html。
- **为什么提高 z-index 无效**（实测 7 种方案全败：`z-index:2000`、`isolation:isolate`、`position:fixed`、tabs z=0、utilities z=300、tabs pointer-events:none…）：菜单被困在 utilities 的 **z=2 堆叠上下文**里，而 tabs 是 `position:relative; z-index:1` 且 DOM 在后 → tabs 恒压菜单。
- **有效修法（一条属性）**：`[class*="wSkVaW_headerUtilities"] { overflow: visible }` → 菜单按宿主原本的定位绘制出来；真实触摸点击菜单项 → 菜单关闭并打开导出对话框（`menus 1→0, dialogs 1`）。
- **随用户指示隐藏该按钮**：用户指出"导出会话日志已在抽屉页脚做了"，故移动端 `[class*="nL4_yW_moreButton"] { display: none }`（桌面保持官方原样，实测 `moreVisible:true`）。`overflow: visible` 保留——它修的是宿主格子裁自家下拉的 bug，任何插件往同一格子挂下拉都会被裁。
- 验证：`verify-more-menu.mjs` 4/4（按钮在场 → 真实触摸开菜单 → 菜单项可达 → 真实触摸开对话框）；`verify-more-gone.mjs` 3/3（移动端隐藏、尾部无死区 `rowRight 374 / lastChildRight 372`、抽屉 Session log 仍在且可点）。

### 11.4 用户测量的对照结论

用户提供的像素级报告（画布 ≈1240×690）与 DOM 实测**逐项吻合**（1240 ÷ 3.18 ≈ 390 CSS px；其 #1 侧栏开关 48–95 → 15–30 CSS = 我们的 toggle [8,36]；#2 异常字形 308–338 → 97–106 = crumb 起点 80–158 区段）。其"B-1 左侧死区 213px → 67 CSS px"即宿主 header `padding-left:60px`（为已隐藏的 rail 开关预留）+ titleRow 起点，**属宿主设计而非渲染错误**；其 #9 溢出菜单 1108–1152 → 348–362 = `nL4_yW_moreButton` [330,374]，右侧 88px 是截图裁切余量。

## 12. 第五轮：「后台任务运行中 ⌄ 展开失效」取证（2026-09-13）

### 12.1 找到真凶：**是我们自己的两条规则**

| 规则 | 后果 | 证据 |
|---|---|---|
| chip 族 `position: static !important` | 废掉宿主锚点 | 宿主 `dsh-client-ui-jobs` 的面板 CSS 是 `position:absolute; top:calc(100% + 5px); left:0`，**依赖官方 `.root{position:relative}`**；A/B：`static` → 面板 `[8,849]`（视口高 844，**在屏幕外**）且不锚定；`relative` → `[271,57]` 正好在 chip 下方 |
| 同族菜单 `left: 8px !important` | 把面板推出右缘 | chip 在 header 右端（实测右缘 374/390），336px 面板 `left:0` 起于 chip 左缘 → 越界；`left:8px` 夹取实测 `x=350..686`（更糟），`right:8px` 实测 `x=30..366`（在视口内） |

两条都已修：删掉 `position: static`（原为 composer 的 ContextMeter 写，实测该处本就 `relative`、A/B 像素一致，删除无副作用）；菜单改 `left:auto; right:8px`。

```

anchored=true（chip 下缘 52 + 5）   insideViewport=true
```

### 12.3 仍存疑的一层（未在真机确认，不假装已修）

面板顶部（y 57–96）与官方 view-tabs 行（y 52–96）重叠，`elementFromPoint` 命中的是 `wSkVaW_tabs`。**注意：subagent chip 不受影响**——它的菜单 portal 到 `BODY` + `position:fixed`，实测真实触摸开合正常（`[38,49,336,58]` 完全在视口内、绘制栈含自身）。该重叠只在 jobs 的 header 内 `absolute` 形态上观察到，且用合成 fixture 复现不稳定（fixture 的绝对定位与 React 真实渲染不一致），故**不以 fixture 结论当事实**。

### 12.4 方法论教训（本轮最大成本来源）

- **不要用合成 DOM 替代真实渲染去验证定位/叠层**：我先后 4 次用注入 fixture 得出结论，其中至少一次（`top:-40`）是 fixture 位置计算失真导致的误判。
- **确认目标控件存在于被测环境**，再动手：本机 profile 原本没有 live 任务，我在"控件不存在"的环境里排查了很久。建立回路的正确做法是先让目标控件真实出现（起一个真后台任务 + 用有该任务的会话 ID）。
- 反引号（Pitfalls §CSS 模板）本轮连踩三次，已加 `tests/docs-consistency.test.ts` 守卫（每个 CSS 模板必须恰好两个反引号）。
