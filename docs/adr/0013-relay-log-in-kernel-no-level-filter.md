# 0013 — relay 日志纳入统一内核，但级别过滤不作用

状态：Accepted（2026-10-20）

## 背景

统一日志管理（map #221）初期把管辖范围定为三个落盘面（shell.log / webview 日志 / 宿主输出），对抗式审查（#224）指出第四个落盘面被漏掉：`shell-relay.log`——中继进程另写、行带 ISO 时间戳、零轮转、写失败静默，继续无上限增长且保留策略管不到。纳入的方式有讲究：中继进程是独立进程，拿不到壳进程的 `liveSettings` 级别持有者；而 relay 日志是 Windows 上排障的唯一入口，量小但每行都关键。

## 决策

`shell-relay.log` 成为统一内核的**第四个源**：

- 中继进程引用同一 `bun/logging` 内核模块，获得独立 sink 实例，自带跨天 + 大小双触发轮转，归档进同一个 `logs/archive/`；
- **级别过滤不作用 relay 源**：中继进程没有共享级别持有者，且 relay 是 Windows 排障唯一入口，恒定落盘、语义上视为 info；
- 导出、诊断快照、保留清理覆盖 relay 源；壳侧 `writeRelayLog` 委派内核 `writeRelayLine`，其写失败随内核 IO 上报（不再静默）。

## 取舍

- 「级别过滤不作用」是有意的例外而非遗漏：给 relay 做跨进程级别同步（每次写读设置文件或加进程间通知）复杂度不成比例，而过滤收益为负——把 Windows 上仅有的排障线索滤掉，比多写几行日志伤害大。
- 中继进程内嵌脚本里的独立 `log()`（自写文件那段）不在壳进程管辖内，保持原样；内核只接管壳侧写入与轮转/归档/保留，这是本决策的边界。

## 后果

- 归档命名、保留清理、导出选份、诊断快照在四源上行为一致；`list_log_files` 回执的 `active` 含 relay 行。
- relay 活跃字节不计入快照逐源字段的旧口径（`logs.shell`/`logs.webview` 形状红线不动），relay 以归档台账与 `logs.archive` 汇总承载。
