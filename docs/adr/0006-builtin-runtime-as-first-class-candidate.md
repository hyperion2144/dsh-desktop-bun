# ADR-0006: 内置运行时是一等候选——参与更新比较，只多「位置 / 不可卸载 / 不必下载」三条属性

- 状态：Accepted（2026-10-17）
- 关联：issue #138（map #135 的第一张票「更新判定层」）；同图 #140/#139/#142/#141 消费本决策
- 决策人：维护者（2026-10-17 grilling 拍定）

## 背景

壳里其实有两棵 DSH 运行时：**随包内置**的那棵（打进安装包的 `builtinDir`），和用户**下载**到 `<appSupport>/runtimes/<version>/` 的那些。两者都是完整的 `@deepseek-ai/dsh` 树，同样的 `lib/bin.js`、同样的布局，同样能被 `resolveRuntimeSelection` 选中（#97 起 `selectRuntimeVersion({ installed, preferred, builtin })` 已把内置传进选中比较）。

但旧代码把它们当成两种东西：面板上「内置」是一个**特殊行**（`isBuiltin`，不显示下载/卸载），更新目录又只从远端拉（`list_runtime_catalog` → npm / GitHub Releases），而这份目录**通常也含内置那一版的版本号**。于是同一个版本号在界面上出现两次：一次是「内置」行，一次是目录里「可下载」的一行。

用户报的困惑正是从这里来的：`.2` 明明是内置的，为什么要去已装目录找，还回退到 `.1`。一旦要做「有没有更新」的通知（map #135），这个双重身份就必须先钉死，否则会出现两种都很糟的结果：把内置重复下载一份占磁盘，以及提醒里说「可下载 X」而 X 就在包里。

#138 要回答的不是「内置能不能被选中」（#97 已经答了），而是**它在新的一层里算什么**：候选？比较对象？还是一个要被排除的特例？

## 决策

1. **内置运行时是一等候选**：版本号进候选集、参与版本比较、参与「比在跑的更新」的判定。它与其他运行时唯一的差别是三条属性——
   - 位置在 `builtinDir` 而非 `runtimesDir`；
   - 面板删不掉（卸载守卫见 `commands.ts` 的 `remove_runtime`：「{version} 是内置版本，不可删除」）；
   - 不需要下载（也不接受下载）。
   这三条属性是**条目上的字段**（`RuntimeUpdateEntry` 的 `source` / `local` / `uninstallable` / `action`），不是一条平行的判定分支。
2. **与内置版本号相同的已下载条目合并成一条**（来源=内置；2026-10-19 修订：合并在判定层产出的归一候选集 `candidates` 上——内置 ∪ 已下载 ∪ 目录去重降序后同号只余一条）。不重复列、不重复下载；那棵已下载的树仍然可以用（用户当年手动下过），但作为「更新候选」只呈现一份，指向内置。切换面（托盘 / 面板）只消费 `candidates`，不得再各自并集去重。
3. **不存在「把内置版本下载下来覆盖内置树」的做法**。与内置不同的任何版本一律走 `runtime-install.ts` 的下载路径，写进已下载目录。
4. **比较基准是实际在跑的版本**（`runtimeSnapshot().running.version`），不是设置里的偏好值。偏好可能高于实际（设了没切、下载失败回落）或低于实际（切了没改设置），拿偏好当基准会同时造成误报和漏报。拿不到在跑版本就不判定（静默），绝不用别的值凑数。
5. **判定只有一处实现**：`desktop-electrobun/src/shared/runtime-update.ts` 的 `evaluateRuntimeUpdates()`（纯逻辑，不 import electrobun）。启动提醒（#142）、托盘「检查更新」（#141）、设置面板（#136）都调它，谁也不许写第二遍版本比较。2026-10-19 修订（#186/#189）：判定层同时产出 `candidates`（全量归一候选，切换面消费）与 `entries`（严格高于基准的更新，提醒面消费）；`installable` 只过滤 `entries` 的 remote 段、IO 留在调用方（service 两遍判定经 `remoteRuntimeCandidates()` 取未下载候选）；`builtinDescriptor`（bundled / external / none）是显示层例外——dev 外部树只进 descriptor，不进候选集。

## 后果

- 正面：内置升级（发新版壳带来更新的内置运行时）第一次能被正确地说出来——它不再需要「先发目录、再让用户下载一份本地已有」的绕路。目录里那份与内置同号的条目也不再诱导用户做一次无意义的下载。
- 代价：候选模型多了一个 `source` 维度，三处消费方都要按它分文案与动作；`installed` 与 `builtin` 的并集语义要写进文档与测试（否则下一个改这里的人会把 `builtin` 特判成「排除」）。
- 风险下限：内置那一项**不依赖远端目录可达**——离线时内置依然是真候选（测试「内置不进远端目录也照样是候选」钉住这条）。反过来，目录拉挂时报错原因会随报告透传，不会静默宣称「已是最新」而把失败藏起来（是否弹窗是 #142 的策略，不在本层）。
- 回退：把 `evaluateRuntimeUpdates` 里的 `candidates` 去掉 `builtin` 一行即可退回「内置不算更新」，代价是内置升级静默丢失。

## 验证边界

纯逻辑，用桩数据钉死（`desktop-electrobun/test/runtime-update.test.ts`，20 例）：内置比在跑的新 / 在跑的比内置新 / 同号合并 / 已下载未切换 / 已下载且在用 / 已下载的旧版本 / 目录拉取失败（两种：本地无更高版本、本地有更高版本）/ dev 无内置且无已下载目录 / 拿不到基准时静默 / 坏版本号丢弃不抛 / 多条更新降序与预发布次序 / 每条更新的动作链走哪几条 RPC。

不在这层验证（各归各票）：动作链真跑通（#139）、弹窗时机与去重持久化（#142）、托盘入口（#141）。切换两步（`save_desktop_settings` 的 `dsh_runtime` + `dsh_mode`，再 `restart_dsh_service`）与 `desktop-settings.tsx` 的 `handleSwitchRuntime` 逐字同款——内置行也写版本号，写 null 会让壳把「切回内置」当成没设置，进而拿已装最高版本顶上（#97 踩过）。
